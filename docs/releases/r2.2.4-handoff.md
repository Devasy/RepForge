# r2.2.4 handoff: scoped rollback after Health Connect review

## User-approved scope

Prepare a handoff only in the current chat. Implementation and release remain for the next task.

The user's explicit choice on 14 November 2026 was: **"Revert only 2.2.3 additions; retain existing HRV."** Use **v2.2.2 as the comparison baseline**, not as a request to revert the entire application. Preserve the other r2.2.3 features and functional fixes.

HRV RMSSD permission, reading, readiness scoring and its conditional readiness-details row already existed in v2.2.2. **Retain that existing HRV functionality and permission.** Skin-temperature access was added in v2.2.3 and is the principal rejected-data-type addition to revert/defer here.

New HRV/skin-temperature Home graph work belongs to **r2.3.0**: see [r2.3.0-handoff.md](r2.3.0-handoff.md). WIP branch `codex/health-data-review-visibility`, commit `8707da769488579cb27324bd1b0151d2a1fc24e6`, contains only a plan and intentionally red tests. **Do not cherry-pick that WIP into r2.2.4.**

## Important unresolved release risk

Google's upheld rejection explicitly names **both** `HeartRateVariabilityRmssd` and `SkinTemperature`, stating that reviewers could not verify necessary user-facing uses. Retaining pre-existing HRV is the user's conscious scope decision; the fact that it shipped before is **not** evidence that Google will accept it now. Removing skin-temperature access alone may leave the HRV finding unresolved.

Do not describe this rollback as guaranteed policy compliance or automatically remove HRV against the user's decision. Report any remaining Play rejection clearly. A wider HRV rollback would require revisiting scope with the user.

## Targeted rollback checklist

1. Compare `v2.2.2..origin/main` for the two named data types. Preserve baseline HRV functionality. Do not wholesale revert PR #101 or the broader skin-temperature feature commit, which may contain unrelated work.
2. Remove `android.permission.health.READ_SKIN_TEMPERATURE` from `workout-logger/android/app/src/main/AndroidManifest.xml`; inspect the merged manifest/APK/AAB too so a library or overlay cannot reintroduce it. Keep pre-existing `READ_HEART_RATE_VARIABILITY` per the user's decision.
3. In `lib/services/health_connect_service.dart`, remove skin temperature from runtime permission requests and granted-type reporting. Disable its active read path so direct callers cannot request/query it in this release. Keep the existing interfaces compatible if that avoids unrelated churn. Do not change the HRV component merely because it shares the permission map.
4. In `lib/services/health_data_sync_service.dart`, remove/disable new skin-temperature ingestion and watermark advancement. Verify ordinary sleep/HR/RHR/HRV sync still works. Preserve generic pagination, strict persistence error handling and permission-aware history backfill fixes where other streams depend on them.
5. Update `lib/screens/widgets/profile_sections.dart`: remove claims that current Readiness insights or Sync coach data now collects skin temperature. Review Coach guidance in `lib/services/ai/coach_tool_service.dart`; defer active skin-temperature collection/feature claims from 2.2.3. If historical stored temperature remains queryable, label it as existing saved data rather than ongoing collection.
6. Preserve existing SQLite migration/version compatibility, stored health records and backup import/export. Do not drop temperature tables, destroy prior data, rewind database versions, or undo v11/v12 exercise/PR migrations merely to remove platform access. Storage compatibility is not a new Health Connect permission request.
7. Add r2.2.4 release notes accurately describing the deferred skin-temperature collection and retained HRV. Keep published r2.2.3 notes intact; document the change in the new entry. Defer the proposed Home metric cards to r2.3.0.
