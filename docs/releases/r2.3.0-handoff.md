## Why this work exists

Google rejected the update and upheld the appeal: reviewers could not identify user-facing functionality requiring `HeartRateVariabilityRmssd` and `SkinTemperature`. They requested clearly displayed, necessary features and minimum permission scope. Do not assume that code paths, tests, a declaration or adding charts alone guarantees Play approval.

HRV was **already present in v2.2.2**. It was not introduced by the Fitify/extended-library change in v2.2.3. The earlier appeal advice put too much weight on implementation evidence instead of reviewer-visible behavior.

As of the audited r2.2.3 implementation:

- HRV RMSSD is read by `HealthConnectService`, used by `ReadinessManager` and the readiness calculator, and shown in the readiness details sheet only when it participates in scoring. It requires five baseline days within the prior 14-day window and a recent reading within 48 hours. HRV has a 20% component weight, renormalized over available components. Do not change this formula merely to add a graph.
- Skin-temperature deltas, optional baselines, source and location are persisted for Coach's SQL analysis. There is no dedicated Home temperature graph. This usage currently requires the user to discover sync and configure Coach, which makes it difficult for a reviewer to verify.
- Existing heart-rate and sleep cards hide themselves when their snapshots are unavailable. New HRV and temperature entry points must remain discoverable without requiring a scored readiness baseline or an AI API key.

## Minimum complete feature

1. Add one **HRV (RMSSD)** graph card and one **Skin temperature** graph card after the existing HR/sleep cards on Home. Reuse GlassCard, Geist, theme colors, spacing and the installed chart library. No new chart dependency.
2. Show seven local calendar days through now. Provide the actual daily average, unit, measurement date, and a graph. A single valid reading must be visible even with fewer than five baseline days. No fabricated measurements or zero-filled missing days.
3. Keep permission-required, unavailable platform/data type, loading, no measurements and failed reads distinguishable. Provide metric-specific access and refresh actions and recheck permissions when the app resumes. Requests must be tied to the feature the user selected; do not silently request unrelated data.
4. Keep existing readiness scoring and stored history. Raw HRV trends must not depend on readiness's baseline threshold.
5. Keep temperature sources and measurement locations separate. With a source baseline, reconstruct absolute skin temperature as baseline + delta. Never represent a delta as absolute or core body temperature. Without a baseline, label a delta-only series clearly and do not connect samples from different source-record baselines into a supposedly comparable trend.
6. Render large-text/mobile layouts, semantic labels, dates, units and missing-data explanations. Chart gaps must reflect real missing dates rather than evenly spacing all readings as though adjacent.

- Planned `lib/services/health_metrics_service.dart`: read access state, read real records, validate/filter windows, aggregate daily points and separate temperature series. Use strict read behavior for the new charts so platform failures do not become successful empty results.
- Planned `lib/screens/widgets/health_metric_card.dart` and chart component: shared card/state handling for the two metric types.
- `lib/main.dart` and `test/test_utils/test_harness.dart`: wire the service and a matching fake; keep production/test behavior explicit.

- `lib/services/health_data_sync_service.dart`, `sqlite_storage_service.dart`: existing stored health data and source-aware temperature records. Preserve migration/backups and existing data.
